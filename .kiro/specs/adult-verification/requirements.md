# Requirements: 성인인증 시스템 (Adult Verification)

> Generated: 2026-01-03
> Status: Generated (Pending Approval)
> Version: 2.0.0

## Overview

TeddyBear's Room 자사몰의 성인인증(휴대폰 본인확인) 시스템이다. 성인용 상품을 취급하므로 성인만 접근/구매 가능하도록 서버 레벨에서 강제하며, 개인정보 최소 수집 원칙을 준수한다. 간편인증(민간인증서)은 업종 제약이 있어 휴대폰 본인확인 기반으로 설계한다.

### 핵심 목표
- **G1**: 성인 상품에 대해 미성년 접근 및 구매를 서버에서 차단
- **G2**: 정식 본인확인(휴대폰)으로 성인인증 수행
- **G3**: 개인정보 최소 수집/최소 저장 원칙 준수
- **G4**: 인증 과정 이탈률 측정 및 전환 최적화 가능
- **G5**: 장애/실패/예외 상황에서 운영 가능한 로그/모니터링/롤백 제공

### 핵심 의사결정
- **D1**: 성인인증 트리거 = 옵션 A (회원가입 시 동시 인증) - 휴대폰 본인확인 기반
- **D2**: 회원만 구매, 성인인증 미완료 시 회원가입 완료 불가 (가입 = 인증 통합)
- **D3**: 성인인증 유효기간 1년, 만료 시 재인증 요구

---

## Requirements

### 1. 계정 상태 모델 (User State Model)

#### Requirement 1.1: 사용자 성인인증 상태 구분
시스템은 모든 사용자에 대해 성인인증 상태를 다음 중 하나로 구분해야 한다:
- `ACTIVE_ADULT`: 회원가입 완료 (성인인증 통과 = 가입 완료)
- `EXPIRED_ADULT`: 성인인증 만료 (1년 경과 시)

**Acceptance Criteria (EARS)**:
- AC1.1.1: 시스템은 회원가입 과정에서 휴대폰 본인확인을 통해 성인인증을 완료해야만 가입을 허용해야 한다.
- AC1.1.2: 성인인증 통과 후 시스템은 `adult_verified=true`, `adult_verified_at=현재시각`을 저장하고 회원 생성을 완료해야 한다.
- AC1.1.3: 시스템은 사용자별 `adult_verified` (boolean), `adult_verified_at` (datetime) 필드를 유지해야 한다.
- AC1.1.4: 미성년자(만 19세 미만)가 본인확인을 시도하면 시스템은 회원가입을 거부하고 안내 메시지를 표시해야 한다.

#### Requirement 1.2: 성인인증 유효기간 관리
시스템은 성인인증의 유효기간을 관리해야 한다.

**Acceptance Criteria (EARS)**:
- AC1.2.1: 성인인증 완료 후 1년이 경과하면 시스템은 해당 사용자를 재인증 필요 상태로 처리해야 한다.
- AC1.2.2: 재인증이 필요한 사용자가 성인구역에 접근하면 시스템은 재인증 요청을 표시해야 한다.
- AC1.2.3: 재인증 성공 시 시스템은 `adult_verified_at`을 현재 시각으로 갱신해야 한다.

#### Requirement 1.3: 인증 실패 시 가입 취소
시스템은 성인인증 과정에서 실패하거나 이탈한 경우 적절히 처리해야 한다.

**Acceptance Criteria (EARS)**:
- AC1.3.1: 성인인증에 실패하면 시스템은 회원 계정을 생성하지 않아야 한다.
- AC1.3.2: 인증 과정에서 사용자가 이탈하면 시스템은 임시 데이터를 정리해야 한다.

### 2. 접근/구매 차단 (Access Control)

#### Requirement 2.1: 성인구역 서버 레벨 차단
시스템은 성인인증 미완료 사용자의 성인구역 접근을 서버에서 차단해야 한다.

**Acceptance Criteria (EARS)**:
- AC2.1.1: 성인인증 미완료 사용자가 성인 카테고리 API를 호출하면 시스템은 403 Forbidden과 인증 안내를 반환해야 한다.
- AC2.1.2: 성인인증 미완료 사용자가 성인 상품 상세 API를 호출하면 시스템은 403 Forbidden과 인증 안내를 반환해야 한다.
- AC2.1.3: 직접 URL 접근 또는 직접 API 호출 시도도 동일하게 차단해야 한다.

#### Requirement 2.2: 장바구니/주문 차단
시스템은 성인 상품이 포함된 장바구니/주문 관련 API 접근을 차단해야 한다.

**Acceptance Criteria (EARS)**:
- AC2.2.1: 성인인증 미완료 사용자가 성인 상품을 장바구니에 추가하면 시스템은 요청을 거부하고 인증 안내를 반환해야 한다.
- AC2.2.2: 장바구니에 성인 상품이 포함된 경우 성인인증 미완료 사용자의 주문서 조회/결제 API 호출을 시스템은 거부해야 한다.
- AC2.2.3: 성인인증 미완료 사용자가 성인 상품의 후기/문의를 조회하려 하면 시스템은 접근을 차단해야 한다.

#### Requirement 2.3: 회원가입 통합 인증 (기본 방식)
시스템은 회원가입 과정에서 휴대폰 본인확인을 통해 성인인증을 수행해야 한다.

**Acceptance Criteria (EARS)**:
- AC2.3.1: 사용자가 회원가입을 시작하면 시스템은 휴대폰 본인확인 과정을 포함해야 한다.
- AC2.3.2: 본인확인 결과 만 19세 이상인 경우에만 시스템은 회원가입을 완료해야 한다.
- AC2.3.3: 본인확인 결과 만 19세 미만인 경우 시스템은 "만 19세 이상만 이용 가능" 메시지를 표시하고 가입을 거부해야 한다.
- AC2.3.4: 시스템은 PortOne SDK를 통해 휴대폰 본인확인 제공사(KCP/다날)와 연동해야 한다.

### 3. 회원가입 성인인증 플로우 (Registration + Verification Flow)

#### Requirement 3.1: 회원가입 플로우 통합
시스템은 회원가입 과정에서 휴대폰 본인확인을 필수 단계로 포함해야 한다.

**Acceptance Criteria (EARS)**:
- AC3.1.1: 사용자가 회원가입 폼을 제출하면 시스템은 PortOne 본인확인 SDK 팝업을 호출해야 한다.
- AC3.1.2: 시스템은 인증 요청 시 고유 identityVerificationId와 state를 생성해야 한다.
- AC3.1.3: 본인확인 완료 후 시스템은 서버에서 PortOne API로 인증 결과를 검증해야 한다.
- AC3.1.4: 본인확인 성공 및 만 19세 이상 확인 후 시스템은 회원 계정을 생성하고 자동 로그인 처리해야 한다.

#### Requirement 3.2: 성인 판정 및 회원 생성
시스템은 본인확인 결과를 기반으로 만 19세 이상 여부를 판정하고 회원을 생성해야 한다.

**Acceptance Criteria (EARS)**:
- AC3.2.1: 본인확인 결과에서 생년월일을 확인하여 만 19세 이상인 경우 시스템은 회원 계정을 생성해야 한다.
- AC3.2.2: 만 19세 미만인 경우 시스템은 회원가입을 거부하고 "만 19세 이상만 이용 가능" 메시지를 표시해야 한다.
- AC3.2.3: 회원 생성 시 시스템은 `adult_verified=true`, `adult_verified_at=현재시각`, `adult_verify_method="PHONE"`, `adult_verify_provider`, `adult_verify_txid`를 저장해야 한다.
- AC3.2.4: 회원 생성 완료 후 시스템은 Supabase Auth를 통해 자동 로그인 처리해야 한다.

#### Requirement 3.3: 인증 실패 및 미성년자 처리
시스템은 인증 실패 또는 미성년자 판정 시 적절히 처리해야 한다.

**Acceptance Criteria (EARS)**:
- AC3.3.1: 인증 실패 시 시스템은 일반화된 에러 코드(정보불일치/통신오류/사용자취소 등)를 반환해야 한다.
- AC3.3.2: 미성년자 판정 시 시스템은 "만 19세 이상만 이용 가능합니다" 메시지를 표시해야 한다.
- AC3.3.3: 시스템은 실패 사유에 따른 재시도 안내 문구를 제공해야 한다.
- AC3.3.4: 민감한 실패 상세 정보는 사용자에게 노출하지 않아야 한다.

### 4. 데이터 저장 정책 (Data Policy)

#### Requirement 4.1: 최소 저장 원칙
시스템은 성인인증 관련 데이터를 최소한으로 저장해야 한다.

**Acceptance Criteria (EARS)**:
- AC4.1.1: 시스템은 다음 필드만 저장해야 한다: `adult_verified`, `adult_verified_at`, `adult_verify_method`, `adult_verify_provider`, `adult_verify_txid`
- AC4.1.2: 생년월일 전체, 주민번호, 카드번호 등 민감정보는 저장하지 않아야 한다.
- AC4.1.3: CI(연계정보)는 필요 시 해시 처리하여 저장하고, 원문은 저장하지 않아야 한다.

#### Requirement 4.2: 로그 보관 정책
시스템은 인증 이벤트 로그를 정해진 기간 동안 보관하고 이후 파기해야 한다.

**Acceptance Criteria (EARS)**:
- AC4.2.1: 인증 이벤트 로그는 최대 1년간 보관해야 한다.
- AC4.2.2: 보관 기간 만료 후 시스템은 로그를 자동 파기해야 한다.
- AC4.2.3: 로그에는 개인 식별 정보를 최소화하고, 내부 user_id만 기록해야 한다.

---

### 5. 보안 (Security)

#### Requirement 5.1: 요청 위조 방지
시스템은 인증 요청/콜백의 위조 및 리플레이 공격을 방지해야 한다.

**Acceptance Criteria (EARS)**:
- AC5.1.1: 인증 요청 시 시스템은 고유 state/nonce 값을 생성하고 세션에 저장해야 한다.
- AC5.1.2: 콜백 수신 시 시스템은 state 값을 검증하고, 불일치 시 요청을 거부해야 한다.
- AC5.1.3: 동일 txid로 중복 콜백 수신 시 시스템은 중복 처리를 방지해야 한다.

#### Requirement 5.2: 접근 권한 제어
시스템은 인증 로그 및 관리 기능에 대한 접근을 제한해야 한다.

**Acceptance Criteria (EARS)**:
- AC5.2.1: 인증 이벤트 로그 조회는 ADMIN 권한 이상 사용자만 가능해야 한다.
- AC5.2.2: 사용자의 성인인증 상태 수동 변경은 SUPER_ADMIN 권한만 가능해야 한다.

---

### 6. 모니터링/로깅 (Observability)

#### Requirement 6.1: 인증 이벤트 로깅
시스템은 성인인증 관련 이벤트를 로깅해야 한다.

**Acceptance Criteria (EARS)**:
- AC6.1.1: 시스템은 다음 이벤트를 로깅해야 한다: 인증 시작, 인증 성공, 인증 실패
- AC6.1.2: 각 로그에는 timestamp, user_id, txid, event_type, failure_code(실패 시)를 포함해야 한다.
- AC6.1.3: 개인정보(이름, 전화번호, 생년월일)는 로그에 기록하지 않아야 한다.

#### Requirement 6.2: KPI 지표 수집
시스템은 핵심 성과 지표를 수집해야 한다.

**Acceptance Criteria (EARS)**:
- AC6.2.1: 시스템은 인증 시작 대비 성공률을 측정해야 한다.
- AC6.2.2: 시스템은 인증 단계별 이탈률을 측정해야 한다.
- AC6.2.3: 시스템은 서버/제공사별 오류율을 측정해야 한다.
- AC6.2.4: 시스템은 성인구역 진입 대비 구매 전환율을 측정해야 한다.

#### Requirement 6.3: 알림 임계치
시스템은 이상 징후 발생 시 운영팀에 알림을 발송해야 한다.

**Acceptance Criteria (EARS)**:
- AC6.3.1: 성공률이 80% 미만으로 떨어지면 시스템은 경고 알림을 발송해야 한다.
- AC6.3.2: 오류율이 10%를 초과하면 시스템은 긴급 알림을 발송해야 한다.
- AC6.3.3: 콜백 실패가 5분간 10건 이상 발생하면 시스템은 알림을 발송해야 한다.

### 7. 규정 준수 (Compliance)

#### Requirement 7.1: 개인정보처리방침 반영
시스템은 본인확인 서비스 위탁 정보를 개인정보처리방침에 반영해야 한다.

**Acceptance Criteria (EARS)**:
- AC7.1.1: 개인정보처리방침에 본인확인 수탁자, 위탁 업무, 수집 항목, 보관 기간을 명시해야 한다.
- AC7.1.2: 인증 요청 전 시스템은 개인정보 수집/이용 동의를 받아야 한다.

#### Requirement 7.2: 청소년보호정책 반영
시스템은 청소년보호정책에 성인인증 관련 내용을 반영해야 한다.

**Acceptance Criteria (EARS)**:
- AC7.2.1: 청소년보호정책에 성인인증 전 접근/구매 차단 정책을 명시해야 한다.
- AC7.2.2: 우회 방지 및 사후 조치 정책을 문서화해야 한다.

#### Requirement 7.3: 사용자 안내
시스템은 성인인증 관련 사용자 안내를 제공해야 한다.

**Acceptance Criteria (EARS)**:
- AC7.3.1: 인증 요청 화면에 인증 필요 사유, 예상 소요 시간, 최소 정보 처리 안내를 표시해야 한다.
- AC7.3.2: FAQ에 "왜 필요한가", "인증이 안 될 때", "재인증이 필요한 경우"를 포함해야 한다.

---

### 8. 런칭/롤백 (Rollout)

#### Requirement 8.1: 기능 플래그
시스템은 기능 플래그를 통해 점진적 롤아웃을 지원해야 한다.

**Acceptance Criteria (EARS)**:
- AC8.1.1: 시스템은 성인인증 기능 전체의 활성화/비활성화를 기능 플래그로 제어해야 한다.
- AC8.1.2: 시스템은 인증 트리거 방식(옵션 A/B)을 기능 플래그로 전환할 수 있어야 한다.

#### Requirement 8.2: 장애 대응
시스템은 본인확인 제공사 장애 시 안전하게 대응해야 한다.

**Acceptance Criteria (EARS)**:
- AC8.2.1: 제공사 장애 시 시스템은 성인구역 접근을 차단 유지하고 안내 공지를 표시해야 한다.
- AC8.2.2: 장애 복구 후 시스템은 정상 운영으로 자동 전환해야 한다.
- AC8.2.3: 장애 시간대의 인증 시도 실패는 사용자에게 불이익 없이 재시도 가능해야 한다.
